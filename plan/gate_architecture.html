场 · DEMO 游戏场景

桌面地图垫 + 站点 + 互动机制（待你定形态）
  • 导游要有「可导的览」：站点=Datawhale 板块
  • 游客动线：欢迎→带路→讲解→问答
  • 职责：确保 3 分钟体验完整、评委可感
集成层（把三体缝起来）：xiaozhi.me 人设自带机器人动作 MCP（走路/转身/大笑，平台现成）；再挂一个自定义 MCP guide_query → 调智库 ask API。大模型端到端决策：游客提问 → 查智库 → 组织话术 → 下发动作。
⚠️ 唯一技术风险：ESP32 只认 xiaozhi.me 云端，自定义 MCP 必须是公网可达的 URL——mini 在内网，需要穿透（家里有现成 VPS 可当出口）。这是下面 Q2 要定的事。

Q1 · DEMO 场景形态（场怎么搭）

A · 桌面地图垫 + 站点动线
A2 地图垫印 Datawhale「版图」，5-6 个站点牌，科鲸沿路线走站讲解，纯导览不打游戏。成本最低，故事最顺。
B · 地图垫 + 通关集章游戏
在 A 基础上加游戏机制：游客答对站点的问答得「印章贴纸」，集满换小奖品（贴纸/徽章）。互动性最强，备物料稍多。
C · 不搭实体场景，纯互动问答
科鲸站桩，游客自由提问，屏幕配表情字幕。省事但「导游」感弱，评委看到的更像音箱。

Q2 · 智库 API 怎么让云端够得着

A · mini 跑服务 + 家里 VPS 穿透出口
ask.py 包一层 HTTP 跑 mini，kl/la/shanghai VPS 选一台做 frp/反代出口。数据留在 mini，更新即生效。
B · build 导出静态 JSON 挂 VPS
每次改智库后 build 导出 index.json 传 VPS，查询逻辑做成 VPS 上的轻函数。更稳（mini 挂了也不影响），但更新要传文件。
C · 技术细节你定，保证现场能用就行
我按现场可靠性优先原则选，配置过程记录进仓库。

Q3 · 比赛现场网络预案

A · 现场 WiFi 为主 + 手机热点备用
ESP32 配网优先级：现场 WiFi → 热点；演示前实测切换。
B · 全程手机热点
不赌现场网络，直接热点，简单可控。
